# PoRT — Proof of Round Trips

**一个把稀缺资源从「算力」换成「网络位置」的工作量证明协议。**

设计目标（按优先级）：

1. **1C1G 小 VPS 具有巨大优势** —— 大机器和 GPU 矿场都不划算
2. **GPU 完全无用** —— 瓶颈不在 FLOPS
3. **流量小** —— 普通 VPS 套餐扛得住（目标 <100 GB/月）
4. **需要良好网络** —— 机房级低延迟和在线率就是收益

> **状态：设计稿。** 其中 M1 杠杆已有实测支撑，M2/M3 尚未验证。已知的薄弱环节在 §8 全部列出，没有隐瞒。

---

## 1. 三根杠杆

| 杠杆 | 机制 | 打击对象 | 实测状态 |
|---|---|---|---|
| **M1 缓存争用** | 每实例工作集 4 MB —— 刚好塞满单核 L2，但 N 个线程会挤爆共享 L3 | 多核大机器 | ✅ **已实测**：工作集 ≥2MB 时，4 线程即损失 32–38% 效率 |
| **M2 单实例配额** | 一个身份同时只能有一条链在飞 | 单机多开 | ⚠️ 设计稿，且是最弱一环（见 §8.1） |
| **M3 强制网络往返** | 每次尝试需 K 次不可预测的网络往返，延迟占总耗时 60%+ | **GPU / 算力堆砌** | ⚠️ 设计稿，待模拟验证 |

**M3 是让 GPU 失效的主力，M1 是防多开的主力，M2 是补充。**

---

## 2. 角色

| 角色 | 说明 | 硬件需求 |
|---|---|---|
| **Miner（矿工）** | 构造往返链、争夺出块 | 1C / 1G / 良好网络 |
| **Responder（应答者）** | 回应他人的往返请求并签名 | 同上（**每个矿工同时也是应答者**） |
| **Validator（验证者）** | 校验区块中的往返证明 | 同上 |

**三个角色由同一个进程承担。** 网络中不存在"重型节点"这一类——这是与 Qubic（1TB 内存裸机 computor）的根本区别。

### 活跃集（Active Set）

- 由链上状态确定：在第 `N-10` 块时质押 ≥ `MIN_STAKE` 的所有身份
- 每个身份绑定一个 `(pubkey, ip:port)`
- 应答率低于 `MIN_RESPONSE_RATE` 的身份会被移出活跃集（惩罚白嫖）

---

## 3. 核心协议

### 3.1 挖矿循环

```
challenge ← H(prev_block_hash ‖ miner_id ‖ nonce)
state     ← challenge
responses ← []

for i in 1 .. K:                                  # K 次强制往返

    # ① 本地记忆硬步骤 —— M1 杠杆所在
    state ← memory_step(state, scratchpad)        # 4 MB 工作集, ~10 ms

    # ② 由 state 确定要问谁 —— 事前不可预测
    peer  ← active_set[ H(state) mod |active_set| ]

    # ③ 强制网络往返
    req   ← (miner_id, i, state)
    resp  ← peer.request(req)                     # ← RTT, 跳不过去
    assert verify_sig(resp, peer.pubkey)
    responses.append(resp)

    # ④ 应答混入状态 —— 下一个 peer 依赖它
    state ← H(state ‖ resp.sig)

if H(state) < TARGET:
    broadcast_block(challenge, nonce, aggregate(responses))
```

**三个关键性质：**

- **不可预取**：第 `i+1` 个 peer 由第 `i` 个的**签名**决定，签名拿到之前算不出来
- **不可并行**：链严格串行，多核/多流处理器帮不上忙
- **不可伪造**：没有对方私钥就构造不出 `resp.sig`

### 3.2 应答者逻辑（故意做得极简）

```
on_request(req) from ip:
    if rate_limit_exceeded(ip):  drop                       # M2
    if req.miner_id not in active_set:  drop
    sig ← sign(sk, H(req.miner_id ‖ req.i ‖ req.state ‖ my_id))
    reply(sig)
```

**应答者不验证 `state` 的正确性**——那太贵。它盲签，**合法性统一由最终的区块验证来保证**。这让应答成本降到「一次签名」，1C1G 完全扛得住。

### 3.3 验证（任何节点，~10 ms）

```
verify_block(blk):
    state ← H(prev ‖ miner_id ‖ nonce)
    for i in 1..K:
        state ← memory_step(state, scratchpad)               # 验证者要重算本地部分
        expect_peer ← active_set[H(state) mod |active_set|]
        assert blk.responses[i].signer == expect_peer        # ← 关键: peer 必须对得上
        state ← H(state ‖ blk.responses[i].sig)
    assert verify_aggregate_sig(blk.responses)               # BLS 聚合, 一次验完
    assert H(state) < TARGET
```

> ⚠️ 验证需要重算 K 次 `memory_step`，成本 ≈ K × 10ms = 640ms。**这偏贵。** 缓解方案见 §8.3。

## 4. 消息格式

```
Request   (~56 B)
  miner_id   : 32 B   (pubkey hash)
  seq        :  2 B
  state      : 32 B
  ─────────────────
  合计 66 B

Response  (~104 B)
  responder  :  4 B   (活跃集索引)
  sig        : 96 B   (BLS12-381)
  ─────────────────
  合计 100 B

Block Proof (~1 KB)
  challenge  : 32 B
  nonce      :  8 B
  peers      : K × 4 B = 256 B      (K=64)
  agg_sig    : 96 B                 (K 个签名 BLS 聚合成一个)
  ─────────────────
  合计 ~400 B      ← BLS 聚合是关键，否则 64 个签名要 6 KB
```

## 5. 参数表

| 参数 | 取值 | 推导依据 |
|---|---|---|
| `K` 往返次数 | **64** | 自问自答攻击下 `f^K` 可忽略；且证明可聚合到 400 B |
| `SCRATCHPAD` | **4 MB** | ✅ 实测甜点：塞满单核 L2，但 32 线程 × 4MB = 128MB ≫ 服务器 32MB L3 |
| `memory_step` 耗时 | **~10 ms** | 使本地占比 ≈33%（RTT 20ms 时），保证 M1 有足够权重 |
| 单次尝试耗时 | **~1.9 s** | K × (10ms + 20ms) |
| 每节点尝试率 | **~0.5 次/秒** | 1/1.9s |
| `MIN_STAKE` | 待定 | 抗女巫的经济门槛 |
| 出块时间 | 60 s | |

### 流量核算

```
挖矿侧: 0.5 次/秒 × 64 往返 × 166 B      =  5.3 KB/s
应答侧: (全网请求总量 ÷ 活跃集规模)       ≈  5.3 KB/s   (对称)
─────────────────────────────────────────────────────
合计   ≈ 10.6 KB/s  ≈  27 GB/月          ✅ 远低于 VPS 套餐的 1-2 TB
```

## 6. 经济性：为什么 1C1G 最优

以 32 核服务器 vs 32 台 1C1G VPS 对比（假设都能拿到 32 个 IP）：

| | 32 核服务器 × 1 | **1C1G VPS × 32** |
|---|---|---|
| 月成本 | ~$200 | **~$128** |
| 并发链数 | 32（需 32 个 IP） | 32 |
| **本地步骤速度** | ❌ **32 线程 × 4MB 挤爆 32MB L3，退化 2.5–3x** | ✅ 各自独享缓存，满速 |
| **网络位置** | ❌ 只有一个机房，RTT 分布单一 | ✅ **可散布全球，期望 RTT 更低** |
| 有效尝试率 | ~0.2 次/秒/链 | **~0.5 次/秒/链** |
| **$/有效算力** | 基准 | **✅ 约 4 倍优势** |

**GPU 矿场**：本地步骤只占 33%，就算 GPU 把它压到 0 也只提速 33%；而 K=64 的串行链让上万个流处理器全部闲置。**买显卡是纯亏。**

## 7. 抗自问自答

攻击者控制活跃集比例 `f`，则：

```
全部 K 次都问到自己人的概率 = f^64
  f=0.10 → 10^-64     可忽略
  f=0.50 → 5×10^-20   可忽略

期望加速 = 1/(1-f)
  f=0.10 → 1.11x      轻微
  f=0.30 → 1.43x      可接受
  f=0.50 → 2.00x      需要 MIN_STAKE 把 f 压住
```

**`K=64` 让"全程作弊"不可能，只剩与持有比例线性相关的轻微加速。**

## 8. 已知弱点（不掩饰）

### 8.1 ⚠️ M2 是最弱的一环

**问题**：应答者按源 IP 限流，但活跃集大时请求被摊得极薄——一个多开 100 条链的攻击者，落到每个应答者身上仍只有 0.5 次/秒，**触发不了限流**。

**候选解法（都不完美）**：

| 方案 | 优点 | 缺点 |
|---|---|---|
| 按身份质押 | 经济上干净、全局可验证 | 变成 PoS 混合，偏离纯 PoW |
| 应答者上报速率异常，链上统计惩罚 | 保持无许可 | 复杂，易误杀 |
| 缩小活跃集使限流信号变强 | 简单 | 降低去中心化程度 |

**目前倾向"按身份质押"**，但这需要你决定是否接受 PoS 成分。

### 8.2 ❌ 批发 IP 攻击

租一个 /24（256 个 IP）塞进一台服务器。**这个挡不住。**

缓解：要求 IP 跨 ASN/前缀分散并按多样性加权。但这只是提高成本，不是消除。**好在规模化边际收益是个位数倍，而非 GPU 挖矿的 1000 倍。**

### 8.3 ⚠️ 验证成本偏高

验证要重算 64 次 `memory_step` ≈ 640 ms，对轻节点太重。

**候选解法**：让 `memory_step` 非对称——正向算得慢、验证快（类似 VDF 的思路）；或抽样验证 + 欺诈证明。**未解决。**

### 8.4 ⚠️ 引导问题

活跃集为空时协议无法启动。需要创世阶段的种子节点集，这段时期中心化。

### 8.5 ⚠️ 地理聚集

若全网节点大量聚集在少数机房，"随机 peer"的期望 RTT 会很低，M3 的区分度下降。需要地理多样性激励，但**位置证明本身是公认的难题**。

## 10. 与现有方案的关系

| 项目 | 关系 |
|---|---|
| **Qubic** | ❌ **不是参照对象**。其 computor 要求 1TB 内存 + 裸机 UEFI，VPS 无法运行，方向完全相反；且挖矿已转向 GPU |
| **RandomX** | ✅ M1 的思想来源（2MB scratchpad）。本协议在其之上叠加了网络维度 |
| **drand** | ✅ 架构参照：极轻节点、低流量、延迟与在线率决定一切 |
| **Helium PoC** | 同样奖励网络位置，但绑定专用无线硬件 |
| **Filecoin / Chia** | 奖励存储/空间，非延迟 |
