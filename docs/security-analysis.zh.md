# NarrowNet — 攻击面分析（实测标定版）

**版本**：v3 / 已用 Numba(LLVM JIT) 原生代码实测标定
**测试机**：Intel Core Ultra 5 125H（Meteor Lake，**无 AVX-512**），绑定 P 核 CPU0，实测 4.25 GHz

**一句话**：把神经网络推理做成「窄而极深」的形态，让攻击者无法通过 GPU/ASIC 获得数量级加速。

> ⚠️ **本版本推翻了上一版的多项结论。** 上一版基于「55 周期/步」的估算模型，实测发现真实成本是 **829–1043 周期/步**，模型偏差 15 倍。所有受影响的结论已修正，修正处均标注 ❗。

## 1. 算法结构（v3）

```
阶段1 — 廉价整数顺序填池（每 nonce 独立，CoW 免疫）
  x,y ← SHA256(seed ‖ nonce)
  for i in 0 .. N-1:
      (x,y) ← xorshift128+(x,y)          # 顺序依赖，不可并行填
      v ← x + y
      j ← v & (N-1)                      # 全域随机回读
      v ← (v ⊕ bits(pool[j])) × φ
      pool[i] ← map_to_unit(v)           # 映射到 [-1,1)，避开 denormal

阶段2 — 神经主链（指针追逐）
  for t in 0 .. D-1:
      blk ← fnv(h) & (N/64 - 1)          # 位掩码，非取模
      W_t ← pool[blk·64 : blk·64+64]     # 8×8 权重块 = 512B = 8 个缓存行
      h   ← act(W_t·h + h)               # 残差连接，FP64
      pool[blk·64] ← mix(…, h[0])        # 写回

act(h) = normalize( h>0 ? h/(1+|h|) : 0.05h )
```

**v3 相对 v2 的改动**：
- 池子取 2 的幂 → 取模变位掩码，省 30–90 周期/步
- 填池改用整数链（原为神经链）→ **快 10 倍**，且不损失 CoW 免疫性
- 去掉偏置，改用**残差连接** → 权重块正好 64 double（对齐 8 缓存行），且残差是 ResNet/Transformer 的标准结构

## 2. 实测数据

### 2.1 主链成本（内存杠杆验证）

| 池子 | ns/步 | 周期/步 | 相对 2MB | 缓存层级 |
|---|---|---|---|---|
| 2 MB | 65.4 | 278 | 1.00x | L2 |
| 16 MB | 130.2 | 553 | 1.99x | L3 |
| 64 MB | 212.3 | 902 | 3.25x | 超出 L3 → DRAM |
| 256 MB | 245.5 | 1043 | **3.75x** | DRAM |

✅ **内存杠杆经实测确认有效**：池子从 2MB 增到 256MB，每步成本上升 3.75 倍。

### 2.2 成本构成（为什么是 900 周期而不是 55）

❗ 原模型漏算了两个大头：

| 项 | 实际代价 |
|---|---|
| **8 次 FP64 除法**（每分量一次 `v/(1+\|v\|)`） | 50–110 周期，x86 上除法延迟 13–14 且流水化差 |
| **64 位取模**（v3 已改为位掩码消除） | 30–90 周期，整数除法完全不流水 |
| sqrt + 最终倒数 | ~30 周期 |
| 8×8 矩阵乘（64 FMA） | 40–60 周期 |
| 随机访存 | 15（L2）→ 300+（DRAM） |

### 2.3 填池成本

| 池子 | 耗时 | ns/double | 周期/double |
|---|---|---|---|
| 16 MB | 13.9 ms | 6.62 | 28.1 |
| 64 MB | 110.8 ms | 13.21 | 56.1 |

## 3. 防线清单（含新发现）

| # | 防线 | 挡什么 | 强度 | 能被什么削弱 |
|---|---|---|---|---|
| **D1** | **每链独占内存池** | GPU 并行度锁死为 `显存 ÷ 池子` | ⭐⭐⭐⭐⭐ | ❗池子 <1GB 则不足（见 §5.1） |
| **D2** | FP64 严格 IEEE | 消费级 GPU 的 FP64 是 1/64 速率 | ⭐⭐⭐⭐ | 数据中心卡全速 FP64 |
| **D10** | **FP64 除法（新发现）** ❗ | 每步 8 次除法；GPU 上 FP64 除法要多指令展开，惩罚在 1/64 速率之上再叠加 | ⭐⭐⭐⭐ | 无已知绕过 |
| **D3** | 串行依赖链 | 单链无法并行 | ⭐⭐⭐⭐ | 不挡「一线程一 nonce」吞吐攻击 |
| **D4** | 指针追逐 | 地址依赖上层输出，无法预取 | ⭐⭐⭐⭐ | 池子进缓存则失效（实测 2MB vs 256MB 差 3.75x） |
| **D5** | 每 nonce 独立池（CoW 免疫） | 堵住写时复制绕过 D1 | ⭐⭐⭐⭐⭐ | 实测 0/2,097,152 条目相同，无已知绕过 |
| **D6** | 读-改-写回 | 关掉预取，强制池子可变 | ⭐⭐⭐ | — |
| **D7** | 分支非线性 | warp 发散 | ⭐⭐ | 可用无分支算术改写 |
| **D8** | ~~窄宽度 (8)~~ | ~~填不满 warp~~ | ❌ **纸老虎** | 「一线程一 nonce」下完全失效 |
| **D9** | ~~kernel launch 开销~~ | ~~每层 5µs~~ | ❌ **纸老虎** | megakernel 下完全失效 |

**D10 是本次标定的意外收获**：为数值稳定加的除法，恰好是一根强反 GPU 杠杆——之前完全没算进来。

## 4. 攻击矩阵

| 攻击 | 手法 | 我方应对 | 结论 |
|---|---|---|---|
| **A1 一线程一 nonce** | persistent megakernel | D1 锁死并行度 | ⚠️ 仅在池子 ≥1GB 时挡得住 ❗ |
| **A2 写时复制 (CoW)** | 共享只读池 + delta 表 | D5：每 nonce 池子全异（实测 0% 相同） | ✅ 已修复 |
| **A3 数据中心 GPU** | H100/B200 全速 FP64 | 无法完全挡，靠 $/吞吐 | ⚠️ 部分挡住 |
| **A4 无分支改写** | 算术 predication | D7 本为次要防线 | ⚠️ 可接受 |
| **A5 ASIC** | 专用芯片 + HBM | 内存墙同在，开发成本 $10M+ | ✅ 经济上不成立 |
| **A6 降精度作弊** | 用 FP32 算 | 输出经 SHA256，1 bit 差即失败 | ✅ 天然免疫 |
| **A7 跳步捷径** | 找代数结构跳过中间层 | 非线性+归一化+指针追逐，无已知捷径 | ✅ 但**未经形式化证明** |
| **A8 时空权衡** | 少存多算 | 未标定 | ⚠️ 待测 |

## 5. 参数选择 —— 本节为实测结论，已推翻上一版 ❗

### 5.1 池子大小决定成败

按实测 CPU 成本 × 桌面 AVX-512 修正（÷1.8），对比 GPU（每步 ~420ns，显存受限并发）：

| 池子 | GPU 可并行 | CPU/GPU 吞吐 | $/性能 | 判定 |
|---|---|---|---|---|
| 16 MB | 2,048 | 0.09x | 0.18x | ❌ **GPU 完胜** |
| 64 MB | 512 | 0.22x | 0.45x | ❌ **GPU 胜** |
| 256 MB | 128 | 0.78x | 1.56x | ~ 打平 |
| **1 GB** | **32** | **2.93x** | **5.85x** | ✅ CPU 胜 |
| **2 GB** | **16** | **5.43x** | **10.86x** | ✅ CPU 完胜 |

> ❗ **上一版声称「64MB 时 CPU 优势 2.8x」是错的**，源于把 CPU 成本估成 11 ns/步（实测 212 ns/步，偏差 19 倍）。真实情况是 64MB 时 **GPU 赢 4.5 倍**。

**结论：池子必须 ≥1GB 才有决定性 CPU 优势。**

这独立复现了门罗币 RandomX 选用 **2GB 数据集**的理由——那不是随意取值，而是达成 CPU 优势的必要条件。

### 5.2 推荐参数

| 场景 | 池子 | 深度 | CPU 优势 | 备注 |
|---|---|---|---|---|
| **挖矿 / 服务端** | **2 GB** | 按目标出块时间定 | **5.4x / $10.9x** | 唯一能拿到决定性优势的配置 |
| 服务端（低配） | 1 GB | — | 2.9x / $5.9x | 可接受 |
| 浏览器 | 16–64 MB | ~300K 步 | ❌ **无 CPU 优势** | 见 §5.3 |

### 5.3 浏览器场景：诚实的重新定位 ❗

浏览器分配不了 1GB（手机必崩），因此 **NarrowNet 在浏览器里拿不到 CPU 对 GPU 的优势**。

**但这不代表它没价值——因为「CPU 赢 GPU」本来就不是反爬的正确目标。** 反爬的真正要求是：**攻击者不能相对诚实用户获得数量级加速**。

| 算法 | 攻击者最大加速 | 防线质量 |
|---|---|---|
| **SHA-256**（Anubis 现状） | **~1,000,000x**（ASIC） | ❌ 已被突破 |
| SHA-256 | ~1,000x（GPU） | ❌ |
| **NarrowNet @64MB** | **~4.5x**（GPU） | ✅ 成立 |

**攻击者的优势从 6 个数量级压到不足 1 个数量级** —— 这是 20 万倍的防御质量提升，即使 CPU 并没有"赢"。

这是本方案在浏览器场景**唯一站得住的宣称**，不要夸大成"CPU 更快"。

## 7. 标定方法学（踩过的坑，供复现者参考）

1. **混合架构必须绑核** — Core Ultra 是 4P+8E+2LP-E，Windows 会迁移线程，E 核慢 2–3 倍。未绑核时同一函数测出 183 与 527 ns 两个值。
   `SetThreadAffinityMask` 用 ctypes 调用时**必须声明 argtypes/restype**，否则静默失败返回 0。
2. **取最小值不取平均** — 测延迟的标准做法，滤掉调度与中断干扰。
3. **频率要实测** — 用已知延迟的依赖链反推。未绑核时测出 2.82 和 5.50 GHz 两个矛盾值（125H 睿频上限 4.5），是线程被迁移的信号。
4. **`fastmath=False` 是强制的** — PoW 要求逐位确定性，编译器重排浮点会改变舍入结果。
